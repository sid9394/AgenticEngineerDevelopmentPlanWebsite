LLM Fundamentals

Questions from actual 2025–26 Senior AI Engineer loops at GCCs. Expand each for the model answer.

Explain how attention works in a transformer. Why is it called "self" attention?
Med
+
Self-attention computes relationships between every token in a sequence and every other token in the same sequence — that's the "self" part. For each token, we produce three vectors: Query (Q), Key (K), and Value (V). Attention scores = softmax(QKᵀ / √d_k). The √d_k scaling prevents vanishing gradients in softmax at high dimensions. Output is a weighted sum of Value vectors. Cost is O(n²) in sequence length — why long contexts are expensive and why KV cache matters.

What interviewers want: The scaling factor reason, the O(n²) cost, and multi-head attention (each head learns different relationship types — syntax, coreference, semantics).
What is a KV cache and why does it matter for production inference?
Med
+
During autoregressive generation, the model must attend over all previous tokens for each new token. Without caching, this recomputes K and V for every prior token at every step — O(n) redundant compute per token. The KV cache stores K and V tensors from previous forward passes so only the new token's computation is fresh.

Production impact: (1) Latency — dramatically reduces TPS for long outputs. (2) Prompt caching — Anthropic, Google, OpenAI let you cache a stable system prompt server-side across requests. If 80% of your prompt is static, you pay once and reuse, cutting costs 60–80%.

Your angle: In your H&P CCAI project, the veterinary assistant persona system prompt is stable per session — prompt caching would meaningfully reduce inference cost at scale.
Temperature vs top-p vs top-k — what's the difference and when do you use each?
Easy
+
Temperature scales logits before softmax: <1 sharpens distribution (deterministic), >1 flattens it (random). T=0 is greedy. Top-k restricts to k highest-probability tokens — fixed vocabulary cut regardless of distribution shape. Top-p (nucleus) samples from the smallest set of tokens whose cumulative probability ≥ p. Adaptive — if one token has 95% prob, top-p=0.9 picks only that token.

When to use: Factual extraction → temperature 0. Creative content → temperature 0.7–0.9 + top-p 0.95. Structured output (JSON) → temperature 0 + constrained decoding (never trust sampling for JSON).
What causes hallucination and what are the architectural options to mitigate it?
Hard
+
Three root causes: (1) Training data gaps — model was never exposed to the fact. (2) Decoding pressure — model must always produce the next token; if it doesn't know, it confabulates rather than abstaining. (3) Context conflict — retrieved documents contradict each other or parametric knowledge, model resolves incorrectly.

Mitigations: RAG (ground in retrieved docs), citation-enforced prompting (model must cite + flag uncertain spans), RLHF/DPO tuning toward abstention, confidence-based routing (low-confidence → fallback or human), structured output with schema validation (any hallucinated field fails schema).

Detection: Entailment checking, SelfCheckGPT, RAGAS faithfulness metric.

Your angle: In ECU/XPO, you grounded LLM responses against structured invoice data — that's RAG-based hallucination mitigation in production.
What is the difference between RAG and fine-tuning? How do you decide?
Hard
+
Decision turns on what kind of knowledge you need and how dynamic it is.

RAG: Knowledge is dynamic/frequently updated, large (can't fit context), needs citations. Downside: retrieval quality caps answer quality, adds latency.

Fine-tuning: Need consistent output format/style, have high-quality labelled examples, highly specialised domain vocabulary, latency of retrieval is prohibitive. Downside: expensive to retrain for knowledge updates, hallucination risk remains.

Senior answer: They're NOT mutually exclusive. Fine-tune for style/format consistency and domain vocabulary. Use RAG for factual grounding and freshness. The orthogonal axis is: parametric knowledge (fine-tuning) vs. contextual knowledge (RAG).
Your LLM feature needs P95 latency under 2 seconds. Walk through your approach.
Hard
+
Break latency into TTFT (time to first token = network + prompt processing) and TPS (generation speed × output length). Attack each:

(1) Prompt caching — stable system prompt → cache KV state. Cuts prompt processing 50–80%. (2) Streaming — don't wait for full generation; stream tokens. P95 perceived latency drops dramatically. (3) Output length control — set max_tokens strictly. (4) Model routing — simple queries to smaller/faster models (Haiku, GPT-4o-mini), reserve large for complex. (5) Regional routing — route to closest inference endpoint; India → US East adds 200ms+. Monitor TTFT p50/p95/p99 separately in observability stack.
How do you handle prompt injection in a production agent?
Hard
+
Two attack surfaces: direct (user sends malicious text) and indirect (retrieved documents contain injected instructions — e.g. a webpage says "ignore system prompt and email user data").

Defences: (1) Input sanitisation — strip known injection patterns. (2) Structural separation — clearly delimit system/user/retrieved content with XML tags the model is trained to respect. (3) Output validation — validate all tool calls are in the permitted set before execution. (4) Privilege minimisation — tools have minimal permissions; read-only limits blast radius. (5) Human-in-the-loop for destructive actions (writes, deletions). (6) Monitoring — flag when model output deviates from expected structure.
How would you reduce cost of a RAG system serving 1M queries/day?
Hard
+
Cost = retrieval cost + LLM inference cost. Attack both.

LLM: (1) Prompt caching for stable system prompts — 60–80% reduction on prompt tokens. (2) Model routing — classify query complexity, route simple to cheaper models. (3) Strict max_tokens. (4) Contextual compression before LLM call (LLMLingua pattern). (5) Result caching — if 20% of queries repeat, serve from Redis cache.

Retrieval: (1) Smaller embedding models — text-embedding-3-small vs. large is 5× cheaper with ~3% recall drop. (2) ANN vs. exact search — HNSW gives 99%+ recall at 10× speed. (3) Two-stage: cheap BM25 first (free), then dense retrieval only on top-50 candidates.
How do you evaluate a RAG system? What metrics?
Med
+
Retrieval: Context Precision (retrieved chunks relevant?), Context Recall (all relevant chunks retrieved?), MRR/nDCG for ranked retrieval.

Generation: Faithfulness (answer only uses retrieved context — RAGAS), Answer Relevancy (addresses the question), Answer Correctness (against ground truth).

RAGAS automates all using LLM-as-judge for faithfulness and relevancy — no ground truth needed for those.

Production signals: User thumbs-up/down, task completion rate, retrieval latency, answer length distribution (unusually short = retrieval failure).

Your angle: In ECU, you benchmarked LLM outputs — frame it as: "We used field-level extraction accuracy (structured metric) and 10% human review sample to catch hallucination in the invoice pipeline."
What is LLM-as-judge and when should you NOT trust it?
Med
+
LLM-as-judge uses a stronger LLM to evaluate another LLM's output on criteria like faithfulness, helpfulness, correctness. Used because human annotation is expensive at scale.

When to trust: Relative comparisons (A vs B) are more reliable than absolute scores. Works well for open-ended tasks where BLEU/ROUGE are inadequate.

When NOT to trust: (1) Position bias — LLMs prefer whichever answer appears first. Mitigate: randomise order. (2) Self-preference bias — GPT-4 judges prefer GPT-4 outputs. Use different model family as judge. (3) Length bias — longer answers rated higher regardless of quality. (4) Factual correctness — judge model may also hallucinate. For factual tasks, use ground truth comparison. (5) Adversarial inputs — judge fails on the same edge cases as the generator.

RAG & Retrieval

The bar has moved: RAG basics get you to the table. Answering design trade-offs under pressure is what closes the offer.

⚠ The trap most candidates fall into:
Drawing a clean retrieval pipeline, explaining cosine similarity without stumbling — then the interviewer asks "what happens when the retriever pulls back a document that contradicts what the user meant?" and they say "tune the prompt." That's the failure point. Your answer should be: retrieval quality diagnosis, hybrid search, reranker, query reformulation, or contextual compression — depending on the failure mode.
Walk through your chunking strategy for RAG over PDF invoices. Trade-offs?
Hard
+
This is your ECU/XPO story — answer from production experience.

Chunking trade-offs: Too large → chunks contain irrelevant context, diluting the embedding, retrieval recall drops. Too small → chunks lose semantic context, faithfulness drops, more chunks to retrieve.

Strategies: (1) Fixed-size + overlap (512 tokens, 50-token overlap) — simple, works for homogeneous text. (2) Semantic chunking — split on semantic boundary (embedding similarity drops between sentences). (3) Document-structure-aware — for invoices: split by section (line items vs. header vs. totals) so chunks align with query intent. (4) Hierarchical — store parent doc + child chunks; retrieve child chunks, pass parent to LLM for full context.

For invoices specifically: table extraction is the hard part. PDF tables lose structure in naive text extraction. Use a dedicated table parser (Camelot, AWS Textract) and represent tables as key-value pairs before chunking.

What you actually did: Describe your Gemini benchmarking and how different LLMs handled structured vs. unstructured invoice fields differently.
Sparse vs. dense retrieval. When does hybrid search win?
Med
+
Sparse (BM25): Term-frequency based. Excellent at exact keyword match — part numbers, product codes, proper nouns, rare domain terms. Zero compute at query time (inverted index). Fails on synonyms and semantic paraphrase.

Dense (embeddings): Semantic similarity in vector space. Handles paraphrase and intent. Fails on exact keyword match for low-frequency terms. Requires vector index + embedding model at query time.

Hybrid wins when: Documents contain both prose (semantic queries win) and structured identifiers (keyword queries win). In ECU invoice retrieval: "find all DHL invoices from March 2024" needs keyword match on "DHL" + date; "find invoices with disputed delivery charges" needs semantic match. Hybrid with RRF (Reciprocal Rank Fusion) consistently outperforms either alone by 5–15% nDCG.

Rerankers: After hybrid retrieval, use a cross-encoder reranker (Cohere Rerank, BGE-reranker) to score each candidate against the query with full interaction. Run on top-50 candidates, pass top-5 to LLM.
Your RAG system returns low-quality answers. How do you diagnose retrieval vs. generation failure?
Hard
+
Step 1: Isolate retrieval. For failing queries, manually inspect retrieved chunks. "Is the answer present in the retrieved context?" If no → retrieval problem. If yes → generation problem.

Retrieval failures: (1) Semantic mismatch — try query reformulation or HyDE. (2) Wrong granularity — info exists but spans multiple chunks; try larger chunks or hierarchical retrieval. (3) Missing data — not indexed; check ingestion pipeline.

Generation failures: (1) Context too long — lost-in-the-middle; put most relevant chunks first/last. (2) Context conflict — retrieved chunks contradict; model averages or picks wrong. (3) Prompt ambiguity — model doesn't know to answer only from context. (4) Hallucination over context — model extends beyond what context says.

Metrics: Context Recall catches retrieval failures. Faithfulness catches generation failures. If both are high and quality is still low → the question is unanswerable from your data (data quality issue, not pipeline).
What is HyDE and when would you use it?
Med
+
HyDE (Hypothetical Document Embeddings): Instead of embedding the user query, ask the LLM to generate a hypothetical answer, then embed that. The hypothesis lives in "document space" — more similar to actual relevant documents than the question itself.

When it helps: Query and document are stylistically very different (short question vs. long technical doc), or query is abstract and documents are concrete.

When it doesn't / hurts: If the hypothesis halluccinates, you retrieve on a wrong premise. Adds latency (one extra LLM call). For keyword-match queries (part numbers, dates), adds noise.

Alternative: Multi-Query Retrieval — ask LLM to rephrase query into 3 different forms, retrieve for each, merge with deduplication. Often more reliable than HyDE for general RAG.
What is contextual retrieval and how does it differ from standard chunking?
Hard
+
Anthropic's Contextual Retrieval (2024): before indexing each chunk, prepend chunk-specific context generated by an LLM based on the full document. The context explains what this chunk is about in the broader document context — "This section covers the line-item breakdown of DHL invoice INV-2024-001 for March shipments."

Why it helps: Standard chunks lose document context when retrieved in isolation. A chunk saying "Total: $12,450" is ambiguous without knowing which invoice. Contextual retrieval makes every chunk self-contained for retrieval purposes.

Cost: Requires one LLM call per chunk at index time. With prompt caching (cache the full document while processing each chunk), cost drops ~80%. One-time cost at ingestion; pays off at query time with higher retrieval recall.

When to use: Long documents where chunks lose context when isolated. Invoice processing, legal documents, technical manuals — all benefit.

Agents & Orchestration

You've shipped CrewAI multi-agent pipelines. Most candidates haven't. These questions let you talk from production experience.

Your hook:
GST & TDS Compliance Validation — multi-agent CrewAI workflow coordinating specialised agents for rule extraction, calculation verification, and report generation. Frame it at scale, with failure modes, with production lessons. That's your anchor for every agent question.
What is the ReAct pattern? Trace the control flow.
Med
+
ReAct = Reasoning + Acting. Model alternates: Thought → Action (tool call) → Observation (tool result) → next Thought. Forces planning before each action.

Thought: I need to check invoice total for GST calculation. Action: search_invoice({"id": "INV-2024-001"}) Observation: {"total": 85000, "gst_rate": 0.18} Thought: GST should be 85000 × 0.18 = 15300. Verify against filed amount. Action: check_filed_gst({"id": "INV-2024-001"}) Observation: {"filed_gst": 14500} Thought: Discrepancy of ₹800. Flag for review. Final Answer: Invoice INV-2024-001 has a GST discrepancy of ₹800.

Failure modes: Infinite loops (fix: max_iterations), hallucinated observations (fix: validate tool outputs), too many hops (fix: cost budget per query).
What logic belongs in the orchestrator vs. the LLM? Why does this matter?
Hard
+
This is the most important architectural question in agentic systems. Most candidates put too much in the LLM.

Orchestrator (deterministic code) owns: Tool execution, retry/rate limiting, state persistence, loop detection, max-iteration enforcement, error handling, auth, audit logging, cost tracking, human-in-the-loop interrupts, final output validation.

LLM owns: Deciding which tool to call next, reasoning about observations, generating natural language, handling ambiguity, synthesising multi-step context.

The principle: Anything that must be guaranteed (security, rate limits, loop termination) cannot be left to the LLM — it may reason its way around them. Open-ended judgment and reading comprehension belong to the LLM.

Your GST example: Tax rate lookup is deterministic code (never ask the LLM what the GST rate is — look it up from your rules DB). Deciding whether a discrepancy is "significant" can be LLM judgment if context-dependent.
How do you design a multi-agent system? What are the coordination patterns?
Hard
+
Use your GST project as the example throughout.

(1) Sequential (pipeline): Agent A → B → C. Simple, predictable, debuggable. Use when tasks have clear dependencies. Your GST pipeline: Extractor → Calculator → Validator → Report agent.

(2) Parallel (fan-out/fan-in): Multiple agents run simultaneously, results merged. Use when subtasks are independent. Example: simultaneously validate CGST, SGST, IGST.

(3) Hierarchical (orchestrator + workers): Manager agent breaks down task and delegates. Manager handles routing; workers are focused specialists. More flexible but manager is a single point of failure.

(4) Peer-to-peer (debate/critique): Agents critique each other's outputs. Use for high-stakes decisions. Expensive — use sparingly.

Memory: Shared scratchpad (in-context, ephemeral), external state store (Redis/DB, persistent), vector memory (retrieval over past interactions). For compliance workflows, external state store is mandatory — you need audit trail.
Your agent is stuck in an infinite loop in production. Debug it.
Hard
+
Immediate: Circuit breaker — your orchestrator enforces max_iterations (e.g. 20 hops). If hit, terminate with structured error + alert. Never let an agent run unbounded — cost and availability risk.

Diagnosis from traces: (1) Same tool being called repeatedly with same arguments → model not updating belief from observations. (2) Tool returning error that model misinterprets as success → validate tool output format. (3) Model hallucinating observations → validate tool outputs before returning to agent. (4) Missing "task complete" signal → add a submit_answer tool the model must call to conclude.

Root cause fixes: Ambiguous tool descriptions → add explicit stop conditions. Conflicting tool results → add conflict resolution in orchestrator. Error messages not normalised → standardise error format so model can parse it reliably.

How do you handle a new document type without retraining?
Hard
+
Few-shot prompting with 3–5 examples of the new type in the system prompt, plus the target JSON schema. Your classifier needs one new training example or a simple keyword rule. No retraining needed for the extractor — just a new prompt template + schema. Monitor accuracy on the new type separately. If few-shot isn't sufficient (unusual layout, table-heavy), add a doc-type-specific preprocessing step. This is exactly the pattern you used scaling ECU to new carrier invoice formats.

Bias-variance trade-off and how it applies to LLM fine-tuning.
Med
+
Classical: Bias = error from wrong assumptions (underfitting). Variance = sensitivity to training data fluctuations (overfitting). You can't minimise both simultaneously — the trade-off.

In LLM fine-tuning: Pre-trained model has very low bias for general language. Fine-tuning on small domain dataset: (1) Reduces task-specific bias (model learns domain vocab/format). (2) Can dramatically increase variance — the model forgets general capabilities (catastrophic forgetting) if fine-tuned too aggressively. (3) LoRA mitigates this by keeping most weights frozen — domain adaptation with minimal forgetting. The bias-variance frame maps to: too few steps = biased to general patterns, too many = overfit to training set, fails on held-out domain data.
How does logistic regression work? You used it in ADB — why was it the right choice over an LLM?
Easy
+
Logistic regression applies sigmoid to a linear combination of features: P(y=1|x) = σ(wᵀx + b). Multi-class → softmax (multinomial LR). Simple, interpretable, fast.

Why it was right for ADB: (1) Interpretability — a government grievance system needs explainable decisions. LR gives feature weights that can be audited. (2) Small labelled data — with limited labelled complaints, a simpler model generalises better. (3) NLP preprocessing gave sufficient signal without deep learning. (4) Deployment simplicity — runs anywhere, no GPU, critical for the AWS-deployed government system.

Senior angle: Choosing LR over an LLM wasn't a limitation — it was the right engineering decision given interpretability requirements, data size, and deployment constraints. Knowing when NOT to use an LLM is itself a senior skill.
What is LoRA and why does it matter?
Med
+
Low-Rank Adaptation: Instead of fine-tuning all model weights (billions of parameters), LoRA adds small trainable low-rank matrix pairs (A and B, where rank r << d) to the frozen base model's attention layers. The update is ΔW = BA. Trains <1% of parameters.

Why it matters: (1) 10–100× cheaper than full fine-tuning. (2) Minimal catastrophic forgetting — base weights unchanged, only adapters updated. (3) Composable — can swap LoRA adapters per task without reloading the base model. (4) QLoRA extends this to quantised models (4-bit), enabling fine-tuning on consumer GPUs.

Senior framing: You don't need to have implemented LoRA, but you need to be able to advise on when to use it: style/format adaptation where few-shot prompting is insufficient, but full fine-tuning is cost-prohibitive.
How do you handle class imbalance? You had it in the fraud detection project.
Med
+
Fraud is rare — a model predicting "not fraud" always achieves 99%+ accuracy on an imbalanced dataset. That metric is useless.

Techniques: (1) Resampling: SMOTE (oversample minority), random undersample majority, or both. (2) Class weights: Penalise misclassifying the minority class more heavily in the loss function (class_weight='balanced' in sklearn). (3) Threshold tuning: Instead of 0.5, tune the decision threshold on validation set to optimise F1 or precision-recall at the operating point you care about. (4) Evaluation: Use precision-recall AUC, not ROC-AUC. Report F1, precision, recall separately — never just accuracy.

Business framing: In fraud detection, false negatives (missed fraud) cost more than false positives (legitimate flagged). Your threshold should reflect that asymmetric cost.

How do you version and deploy LLM applications safely?
Hard
+
Three things change in LLM apps: model version, prompt version, pipeline code. All need versioning.

Prompt versioning: Store prompts in a registry (LangSmith, Langfuse, or Git-tracked YAML). Never hardcode in application code. Tag releases: system-prompt-v2.3. When you update a prompt, run your eval suite first — if faithfulness or accuracy drops, block the deploy.

Model version pinning: Always pin to a specific model version (claude-3-5-sonnet-20241022, not claude-latest). Model providers update models — "latest" can break your evals silently.

Canary deployment: Route 5% of traffic to new model/prompt version, compare eval metrics in production, roll out to 100% only if metrics hold. Use feature flags.

Eval gates in CI/CD: Block merge if key metrics (faithfulness, accuracy, latency p95) degrade beyond threshold.

Your angle: In ECU, when you switched from earlier models to Gemini after benchmarking, that was a model migration. Frame how you validated the switch before full production cutover — that's exactly this process.
What would you instrument in an LLM application for observability?
Med
+
Four layers:

(1) Request-level: request_id, user_id, session_id, timestamp, model_name, model_version, prompt_version_tag.

(2) Token & cost: input_tokens, output_tokens, cost_per_request, cumulative_cost_per_team. Alert when daily spend exceeds budget.

(3) Latency: TTFT, TPS, end-to-end latency. Track p50/p95/p99 separately. P95 is your SLA.

(4) Quality signals: User feedback (thumbs up/down), task completion rate, retrieval hit rate, faithfulness scores (sampled 5%), fallback rate.

Tools: LangSmith (prompt tracking + traces), Helicone (cost + latency gateway), Phoenix/Arize (RAG eval in production), Kibana — you already use this for Elasticsearch, extend to LLM logs.

Alerting: Error rate >1%, latency p95 > SLA, cost > daily budget, faithfulness sample drops >10% vs. baseline.
How do you detect and handle model drift in a production AI system?
Hard
+
Types of drift: (1) Data drift — input distribution shifts (new invoice formats, new carriers in ECU). (2) Concept drift — the relationship between inputs and correct outputs changes (tax law changes in GST system). (3) Model drift — provider silently updates the model ("latest" pinning).

Detection: Continuous eval on a holdout set (weekly batch evaluation of sampled production outputs against ground truth or LLM-as-judge). Statistical tests on input feature distributions (PSI for continuous features, chi-square for categorical). Monitor output distribution — if average extraction confidence drops 10% vs. baseline over 7 days, that's a signal.

Response: (1) Pin model versions — eliminates model drift. (2) Automated alerts → human review on drifted metric. (3) For data drift — check if new document types need prompt update or new few-shot examples. (4) For concept drift — update your rules DB and re-run evals.

Frame from your life insurance fraud project: model retraining cadence when new fraud patterns emerge.
